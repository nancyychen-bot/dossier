How I Built Dossier

I kept meeting people at events and forgetting who they were three weeks later. So I built a private CRM that lets me speak a name into the mic and turn it into a searchable contact I can follow up on. Here's how I built it — step by step — using Claude Code, Next.js, and a Notion database.

The Notion database is the source of truth. The Dossier web app (Vercel) reads and writes to it. A custom agent scrapes emails. Poke connects via MCP for iMessage capture.

The problem

I'd meet someone at a dinner, a conference, a friend's gallery opening — have a great conversation — and then completely lose track of them. I'd remember a face and a vibe, not a name. "The architect I talked to about Tokyo" lived nowhere in my phone contacts.

I tried spreadsheets, Apple Contacts, even a paper notebook. None of them survived past the first week. The friction was always too much when I was standing on a sidewalk saying goodbye to someone.

What I wanted was simple: tap a button, say what I remember, and have it saved. Then later, search by what I actually remember — not by an exact name I forgot.

01 — Started with a PRD Decision

Before opening my editor, I opened Claude in the browser and had a conversation about what I was building. Not code — just the product. What problem does it solve? Who's it for? What does v1 include, and what's explicitly out of scope?

"I want to build a personal CRM for keeping track of people I meet. Voice capture so I can record someone right after meeting them. AI search so I can find people by description, not name. Notion as the backend so I can edit contacts from my phone. Help me write a PRD."

Claude pushed back on scope — asked about multi-user vs. single-user, whether I needed auth, what "enrich" meant. By the end, I had a clear PRD that I saved as PRD.md in my project folder.

💡

The PRD became the reference document for the entire build. Every time Claude Code started drifting, I'd say "re-read the PRD" and it would course-correct.

▶
04 — Chose Notion as the database Decision

The obvious choice was Supabase — real Postgres, row-level security, the whole thing. But I kept coming back to one use case: I want to open Notion on my phone and fix a typo in someone's name.

Notion isn't a database in the traditional sense. It's a writing tool with an API bolted on. But for a single-user CRM with a few hundred contacts, that's fine. The tradeoffs:

  • Rate limit: ~3 requests per second. Fine for one person.
  • No nested data: I serialized meetings and follow-ups as JSON inside rich-text fields.
  • Expiring image URLs: Used Vercel Blob for photos instead — permanent URLs.
  • Real-time sync: The app fetches fresh data from Notion on every request — edits in Notion show up instantly in Dossier.
💬

Notion as a backend is wonderful when editing experience matters more than technical purity. The moment you need multi-user or thousands of records, switch to Supabase. For a personal tool? Notion is perfect.

05 — Built the Notion integration Notion

The entire integration lives in one file: lib/notion.ts. It handles fetch all, create, update, and delete (archive). Every API route calls into it.

Setting up Notion took five minutes: create a database with 17 properties, create an integration, share the database with it, copy the database ID from the URL.

The JSON-in-rich-text trick: Notion can't store nested data, but contacts have multiple meetings. The workaround — serialize as JSON in a rich-text field:

// Stored in the "Meetings" rich-text property:
[
  {
    "id": "m-abc123",
    "date": "2026-04-12",
    "location": "Coffee at Sey, Brooklyn",
    "notes": "Talked about her new gallery show..."
  }
]

Notion's rich-text blocks have a 2,000-character limit, so the app chunks longer JSON across multiple blocks and reassembles on read.

🚀

GET /api/people → queries Notion database → converts pages to Person objects

POST /api/people → creates a new Notion page → returns the page ID

PATCH /api/people/[id] → updates page properties

DELETE /api/people/[id] → archives the page (soft delete)

▶
06 — Added voice capture AI

This was the feature that made the whole thing worth building. The Web Speech API handles speech-to-text in the browser, then the raw transcript goes to Claude for parsing.

"Just met Priya Nair, she's a sound artist at the Brooklyn Museum. Met her at the Printed Matter book fair in Chelsea. She mentioned she's working on an installation about urban noise."

Claude extracts: name, role, company, location, city, notes, and a status tag. The response comes back as structured JSON, and the app creates a new person in Notion.

I also added voice capture for meetings — same flow, but for logging a new encounter with an existing contact.

⚠️

The Web Speech API only works in secure contexts — localhost or HTTPS. It won't work on a local network IP. Once deployed to Vercel, it works everywhere.

▶
07 — Added AI-powered semantic search AI

This solves the original problem. When I can't remember a name, I remember context. Dossier's search understands that.

The implementation: format every contact into a one-line summary, send the full roster plus the search query to Claude, get back matching entries ranked by relevance. No embeddings, no vector database — just a well-crafted prompt.

For dozens to hundreds of contacts, the entire roster fits in a single API call.

▶
08 — Added follow-up email drafts AI

Open any contact, click "Draft email," and Claude writes a follow-up based on everything — role, company, every meeting, every note.

This was the easiest feature to build. The hardest part was getting the tone right — nobody wants an email that sounds like AI wrote it.

▶
09 — Built inline editing and bulk operations Build

Every field on the detail page is editable in place — click, type, blur to save. No edit/save button. The update fires a PATCH to Notion on blur.

In the list view, I added an "edit mode" toggle for batch-updating role, company, city, or status tag across multiple contacts. Useful after a conference.

I also added CSV export — download the full roster for backup or use in other tools.

▶
10 — Added password auth Build

This is a personal tool — I don't need OAuth, magic links, or user registration. Just a single password in an environment variable, signed into an HMAC-SHA256 session cookie.

A rate limiter (3 attempts per 15 minutes per IP) blocks brute-force attacks. That's the entire auth system.

What I learned

▶
Write the PRD before you touch code

Every time I skipped the PRD and went straight to "just build it," I ended up backtracking. The PRD doesn't have to be long — one page is fine — but it needs to answer: what is this, who is it for, what does v1 include, what's explicitly out of scope.

▶
Design before code — even a rough mockup

Building from a visual reference is 10x faster than building from a verbal description. The design tokens, typography, grid layout — all decided up front. No iterating on look-and-feel while debugging logic.

▶
Notion works great as a backend — within limits

I can edit contacts from my phone, share the database, see everything in a familiar interface. But: no nested data (hence the JSON hack), rate limits, slow queries, expiring image URLs. Match the tool to what your app actually needs.

▶
Claude does three jobs with one API

Voice parsing, semantic search, and email drafts — same model, different prompts. One Anthropic API key powers all three features.

▶
Commit after every working state

When Claude Code makes a change and it works, commit immediately. Don't batch five features into one commit. I learned this the hard way after losing an afternoon to a cascade of broken code.

▶
When Claude goes off the rails, stop and re-read the PRD

Claude Code will sometimes over-engineer things — adding abstractions you didn't ask for, refactoring working code, scope creep. When that happens: "Stop. Undo the last changes and re-read the PRD." The PRD is your anchor.
